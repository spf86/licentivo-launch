后续复核：原三项已在本地修复，并通过对应回归；以下保留最初审查记录。继续审查发现的 4 项问题见 [授权复查报告](authorization-followup-2026-10-24.md)，这些新增问题尚未修改、未上线。

## AUTH-01：购买同步覆盖 Licentivo 的人工授权限制

优先级：高。修改方：**Licentivo 服务端**。

复现：

1. 创建正常 Launch 购买，兑换设备授权。
2. 通过 Licentivo 的 `PATCH /api/v1/licenses/{id}` 将许可证设为 `suspended`。原设备心跳立即得到 HTTP 403，确认暂停生效。
3. 提交同一购买的新版本 `entitlement.renewed` 快照，没有执行人工恢复。
4. 许可证被改回 `active`，新的身份兑换返回 HTTP 200，并下发设备凭据。

另一条复现先通过相同管理接口将功能清单清空；普通续费同步后，功能又恢复成 `export`、`pro`。

根因：`applyLaunchEvent` 无条件从套餐策略覆盖许可证功能，再把商业事件状态写入许可证状态。现有数据无法区分人工暂停与因购买到期产生的暂停。[实现位置](../../Licenova/internal/httpapi/launch.go#L447)、[人工修改入口](../../Licenova/internal/httpapi/resources.go#L672)。

影响：商家在 Licentivo 中做出的暂停、功能收紧决定，会被之后的普通购买期限同步撤销。这不符合“Licentivo 负责授权决定”的边界。

建议：分开保存商业购买状态与人工授权覆盖，例如人工暂停标记、功能覆盖或拒绝清单。购买同步只更新商业基线，由 Licentivo 合成最终授权；只有明确的人工恢复操作才能清除人工限制。不能简单保留所有 `suspended`，否则正常到期续费也无法恢复。

Launch 和 Launch SDK 无需增加暂停或功能权限判断。

## AUTH-02：签发的离线许可可以超过购买截止时间

优先级：高。修改方：**Licentivo 服务端**。

复现：

1. 同步一笔即将到期的 Launch 购买。
2. 调用 Licentivo 公开的 `POST /api/v1/licenses/{id}/renew` 增加 30 天；该接口接受此 Launch 管理的许可证，但没有同步延长其 Launch 购买记录。
3. 使用真实官方 Go SDK 激活，取得有效签名许可。
4. 到购买截止后，SDK 的 `RunFeature("export")` 仍实际执行了一次业务回调；同一时刻，真实服务端心跳已经返回 HTTP 403。

本次签名许可的截止时间比购买截止晚 **1,185 秒**。这不同于撤销消息尚未抵达离线设备：购买截止在签发时已经存于服务端，却没有成为签名许可的截止上限。

根因：签发逻辑裁剪了许可证自身截止、浮动席位截止和授权会话截止，没有再裁剪到关联的 `LaunchEntitlement.ValidUntil`。直接续期入口允许这两份日期发生分歧。[签发位置](../../Licenova/internal/httpapi/runtime.go#L445)、[直接续期入口](../../Licenova/internal/httpapi/resources.go#L786)。

建议：签发 Launch 授权时，把购买截止纳入统一的最早截止值；同时限制或明确处理 Launch 管理许可证的独立续期、批量续期等入口，保证日期来源一致。还应覆盖历史迁移中许可证日期与购买日期不一致的情况。

Go SDK 本次按服务端签名的许可执行。主要修复应在服务端，不应让 Launch 或 Launch SDK 自行推算购买到期并决定授权。

## AUTH-03：Launch 并发保存套餐映射后，身份指向错误产品

优先级：中。修改方：**Launch 服务端**；Licentivo 可增加映射一致性防护。

后续状态：**Launch 本地已修复并完成回归，尚未上线**。保存映射改为先锁共同产品记录，身份、发布和 SDK 接入配置统一使用稳定产品路由；历史错误数据按购买/发布记录核对，歧义明确报错。详见 [修改与验证记录](product-mapping-fix-2026-10-24.md)。以下保留原始复现证据。

复现：

1. 为同一个 Launch 产品创建两个套餐版本，分别选择不同的 Licentivo 产品。
2. 并发执行两个有效的 `SaveMapping` 请求。在现有冲突查询完成后设置测试屏障，稳定复现两边都查询到“没有冲突”的自然并发顺序，没有修改查询结果。
3. 两个保存都成功，同一 Launch 产品最终存在两个远端产品映射。
4. 实际发布套餐 A、下单并确认付款，购买快照收到 `applied`。
5. 获取客户身份时，代码选择更高版本的草稿套餐 B 的远端产品。官方 SDK 接入层因产品上下文不一致拒绝启动。

另外通过真实 Licentivo 管理接口验证：它接受同一 Launch 产品的两个不同套餐引用分别映射到不同授权产品，因此不能依靠远端接口消除该竞态。

根因：保存时只锁各自的套餐版本，两次事务锁的是不同记录，跨套餐的一致性计数不是原子约束。身份路由又按该产品所有套餐的最大版本选择映射，包含草稿，放大了错误状态的影响。[映射校验](../internal/app/connections.go#L411)、[身份路由](../internal/app/identity.go#L77)。

影响是合法已购客户被错误拒绝授权；本轮没有复现跨账号或跨产品越权放行。SDK 的产品一致性检查在此处正确拒绝了错误上下文。

建议：建立同一 Launch 产品的稳定远端产品绑定，并由数据库约束保证一致性；保存映射时在任何相关一致性读取之前锁定共同的产品记录，而不只锁套餐版本。身份应读取稳定的产品绑定，避免被更高版本草稿改变。Licentivo 可按连接与 Launch 产品增加相同约束作为防护。
