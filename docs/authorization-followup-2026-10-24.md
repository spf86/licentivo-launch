# Launch / Licentivo 授权复查

日期：2026-10-24。本轮确认 4 项问题，仅验证并记录，**没有修改业务代码、没有部署、没有发布 SDK**。建议先处理 AUTH-04、AUTH-05。Launch 继续只提供账号身份、商业购买快照及设备操作入口，授权决定仍在 Licentivo 和官方 SDK。

后续状态：AUTH-07 已在 Launch SDK 本地修复并同步各语言入口；Licentivo 侧提供的 AUTH-04～06 更新也已通过本轮对应回归。两端本机联调通过，均未上线。详见 [退出重试修复与联调记录](logout-retry-fix-2026-10-24.md)。以下保留修复前的复现记录。

## AUTH-04：策略更新后，退款等负向通知无法撤销原授权

**高优先级；主要修改 Licentivo 服务端。**

复现：正常购买并激活后，通过实际管理接口修改原策略的功能，策略版本随之增加。再提交原套餐的 `entitlement.refunded`，处理器因 `LAUNCH_POLICY_CHANGED` 拒绝应用；12 次重试后进入人工核对，原购买仍为 `active`、版本仍是 1。此时不仅旧设备心跳成功，使用新身份启动实际 Go SDK 也能取得新签名许可并执行 `export`。

`entitlement.suspended` 同样复现。另提交截止时间已过去的 `entitlement.expired` 快照，也被策略版本检查挡住，远端仍保留原来更晚的购买截止。这说明问题发生在新的在线授权路径，不能用旧离线许可尚未到期解释。

根因：`applyLaunchEvent` 在处理退款、暂停、到期前，仍要求映射中的策略版本等于当前策略版本；策略编辑会自然打破这个条件。[策略版本检查](../../Licenova/internal/httpapi/launch.go#L410)。Launch 的退款确认与负向快照入队本身不需要重新登记策略，因此无法自动消除远端冲突。

建议：Licentivo 校验连接、购买归属和递增版本后，对已存在购买的退款、暂停、到期独立处理，不要求先完成策略升级或重新匹配。必须原子地更新购买状态并撤销相应会话；不要让配置变更阻止权限收回。Launch 无需接管授权判断。

## AUTH-05：设备占满时，退回低配套餐后仍保留高配权限

**高优先级；主要修改 Licentivo 服务端。**

复现：高配策略允许两个设备及 `pro` 功能，两个设备均已激活。提交退回低配套餐的完整购买快照，低配只允许一个设备且没有 `pro`。远端因 `LAUNCH_DEVICE_LIMIT_CONFLICT` 拒绝应用，12 次重试后仍未降级。购买保留高配套餐，心跳下发的设备上限仍为 2；实际 Go SDK 在原有主机上重新在线激活后，仍能执行 `pro`。

这对应升级退款、套餐回退等正常业务中的设备超额情况。本轮直接验证了低配购买快照，没有通过真实支付渠道执行退款。

根因：新策略设备上限低于当前绑定数时，整个购买快照回滚，高配功能和设备额度一起被保留。[设备数量检查](../../Licenova/internal/httpapi/launch.go#L441)。

建议：由 Licentivo 明确处理超额绑定，例如按确定规则释放超额设备，或先暂停运行、等待客户选择保留设备。已经退回低配的购买不能继续签发高配功能。Launch 继续同步商业结果，不自行挑选、审批或释放设备。

## AUTH-06：普通续费覆盖人工设置的设备上限

**中优先级；主要修改 Licentivo 服务端。**

复现：策略上限为 2，通过实际许可证管理接口将某许可证的 `max_devices` 改为 1。第一个设备激活成功，第二个被拒绝，确认人工限制生效。发送普通续费快照后，设备上限被重置为 2，另一设备使用实际 Go SDK 激活并执行功能成功。

根因：续费直接执行 `lic.MaxDevices = policy.MaxDevices`；人工暂停和功能覆盖已有独立字段，人工设备限制仍没有同等保护。[人工修改](../../Licenova/internal/httpapi/resources.go#L715)、[续费覆盖](../../Licenova/internal/httpapi/launch.go#L452)。

建议：单独保存人工设备上限覆盖，由 Licentivo 合成最终额度。普通续费、升级同步不应无条件清除人工设置，恢复默认应使用明确操作。

## AUTH-07：账号退出失败后丢失重试记录，旧 token 仍有效

**中优先级；已动态确认 Go Launch SDK，主要修改 Launch SDK。**

复现使用实际 Launch HTTP 服务、MySQL 和 Go 账号 SDK；授权运行时使用测试替身：

1. 正常登录，保留原账号 token 用于检查服务端状态。
2. 只让 `/auth/logout` 的请求发生网络错误。第一次退出报告失败，并停止本地运行时、清除账号记录。
3. 恢复网络，再次调用 `Logout`，返回成功，但没有再向 Launch 提交退出请求。
4. 原 token 仍能通过实际服务端认证，并通过真实身份 HTTP 接口取得新的签名身份断言。

根因：`logoutLocked` 无论账号退出是否送达，最后都会 `clearLocked`。后续既没有原会话 token，也没有独立的账号退出待办；Licentivo SDK 的设备退出票据只负责设备解绑，不能补交这个 Launch 账号退出请求。[退出与清理](../pkg/launchclient/application.go#L255)。

影响是服务端旧会话残留；持有原 token 的一方仍可申请身份。本轮没有声称已退出的本地应用还能执行功能，也没有把此账号探针冒充完整的跨服务设备重新激活测试。其他语言 SDK 需要分别验证。

建议：Launch SDK 在清理当前登录状态的同时，单独持久化账号退出待办，直到 Launch 确认撤销；再次退出应恢复提交或明确报告待完成。若不希望保留重试所需的账号凭据，可由 Launch 提供只能撤销该登录会话的专用票据。这仍属于账号安全，不让 Launch 判断许可证、功能或设备授权。
