## AUTH-08：组合故障下，重启恢复已发起退出的会话

复现条件同时包含：账号安全存储的原子替换失败，Launch 账号退出请求未送达，Licentivo 设备退出请求也未送达。仅有普通断网时，之前修复的退出待办机制仍然有效。

复现使用实际 DPAPI 账号存储，在其 `Save` 边界注入写入失败，保留原来的有效 v2 登录记录；两个退出端点通过本机代理模拟不可用：

1. 正常登录并执行实际官方 SDK 的 `export` 回调。
2. 注入上述故障后退出。SDK 报告待完成，当前实例立即停止功能，但账号存储仍是原来的可恢复登录。
3. 关闭并重建 Application，恢复账号存储和账号接口，继续阻断设备退出端点。
4. `Restore` 沿用原 Launch 会话取得新身份断言，实际官方 SDK 再次执行受保护回调。数据库确认没有新建桌面登录，原会话也没有被撤销。

账号层根因：保存退出标记失败后，只在内存保留待办，没有消除原来的可恢复记录。[保存和退出](../pkg/launchclient/application.go#L271)、[恢复](../pkg/launchclient/application.go#L187)。授权 SDK 的本地退出标记使用整段身份 JWT 的哈希区分来源；同一个账号会话重新签发身份后，JWT 改变，旧退出标记没有阻止这次交换。[来源比较](../../Licenova/sdk/go/logout.go#L46)、[哈希来源](../../Licenova/sdk/go/credential.go#L31)。

这不是“退出成功后服务端仍有效”：退出确实报告了错误。缺陷是本地退出意图未能跨重启生效，旧会话被恢复为正常登录，并实际重新取得授权。该组合故障的触发范围应保留在问题描述中。

建议：Launch SDK 的账号退出待办与可恢复登录采用可靠的持久化转换；写入失败时，应尽力使旧登录记录失效，并明确区分“待办已持久化”和“持久化失败”。Licentivo SDK 应以稳定、可校验的授权会话关联退出意图，不能仅凭 JWT 字符串变化就视为新的登录。同一会话的身份刷新应继续受原退出待办约束，用户真正重新登录产生的新会话再按代次处理。授权判断和离线规则继续由 Licentivo SDK 负责。

## AUTH-09：重复排队同一绑定的解绑请求，多扣自助额度

复现：额度为 2，对同一设备、同一绑定代次，在工作进程执行前提交两个不同 `operation_id`。两者都进入 `pending`，随后均标记 `succeeded`。数据库只有一次实际 `deactivate`，额度却从 2 降为 0；对另一个设备的真实解绑被转为 `manual_review / DEVICE_RELEASE_LIMIT`。

相同 `operation_id` 的网络重试已有幂等保护，本问题是两个不同操作编号指向同一个尚未完成的解绑。两个已打开的设备管理页面就可能产生这种请求；前端刷新后隐藏按钮，无法覆盖已经存在的另一页面。

根因：入口仅按操作编号去重，额度按 `pending/succeeded` 操作行计数；工作进程在绑定代次相同但设备已经释放时，仍把第二个操作记为成功。[排队和额度统计](../../Licenova/internal/httpapi/device_sessions.go#L193)、[执行结果](../../Licenova/internal/httpapi/device_sessions.go#L62)。

建议：由 Licentivo 在事务内按许可证、设备绑定和代次合并待处理操作，或对重复释放记录明确的无新增效果结果；自助额度只计一次真实释放。Launch 可以保持操作入口和远端结果展示，不计算解绑资格或额度。

## AUTH-10：旧 Application 实例删除新登录的账号记录

条件：两个 Application 实例共用同一账号存储及产品作用域。

复现：A 登录；B 登录时撤销 A 的服务端会话并保存自己的新登录。随后 A 用内存里的旧会话再次退出，收到 HTTP 401。A 仍先把旧退出待办写入共用存储，再无条件删除该存储键。B 的服务端会话仍然有效，但其本地登录记录已经丢失；重建实例无法恢复账号。

根因：存储键按站点、产品和环境划分，没有登录会话所有权；实例内互斥锁无法保护其他实例。退出标记写入和最终删除都缺少所有权检查。[存储作用域](../pkg/launchclient/application.go#L103)、[退出和清理](../pkg/launchclient/application.go#L262)。

建议：Launch SDK 将每个账号退出待办独立保存，并对当前可恢复登录使用跨实例的原子所有权检查。旧实例只能变更自己的会话记录。只在最后删除前检查不够，之前写退出标记也可能覆盖新登录。该缺陷影响账号恢复，没有复现跨账号取得权限。

## AUTH-11：旧 Licentivo SDK 实例删除新绑定的授权缓存

条件：两个官方 Go SDK 实例共用同一个 `CachePath`。

复现：A 激活；B 使用新的 Launch 登录会话在同一主机激活，得到更高绑定代次并写入机器凭据与许可。A 随后退出：服务端正确把旧退出票据作为过期代次处理，B 的新绑定仍为 active，实际机器凭据心跳返回 200；但 A 无条件删除了 B 的 `.credential.json` 和许可文件，并写入退出标记。只依赖本地机器凭据重建 SDK 时，恢复被拒绝。

根因在本地文件处理，服务端代次保护没有失效。[退出删除凭据](../../Licenova/sdk/go/logout.go#L90)、[清除许可](../../Licenova/sdk/go/client.go#L440)。Launch 内嵌的对应 Go 文件包含相同逻辑。

建议：由 Licentivo SDK 对缓存写入、失效和退出日志增加跨实例所有权或绑定代次保护，或按授权会话分开文件。旧实例只能清理自己仍持有的记录。官方修复后再同步 Launch 的内嵌副本。本轮动态确认 Go，没有把这一结果扩大为所有语言均已复现。
