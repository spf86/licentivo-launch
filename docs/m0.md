# Historical M0 development decisions

Original decision date: 2026-10-15. This is a design baseline and historical record. Use [progress.md](progress.md) for the current implementation and open acceptance work.

## Decisions

| Topic | Decision |
| --- | --- |
| Deployment/data | One merchant instance and database; no shared merchant tenancy or central customer database |
| Stack | Go 1.26, GORM, MySQL, embedded HTML/CSS/JavaScript |
| Schema | Go models are the source; GORM AutoMigrate at startup; no separate schema SQL/versioned migration command |
| License | MIT for project code; retain dependency notices |
| Payments | Stripe and PayPal are both P0; implement one complete path, reuse the ledger for the other, and accept both before release |
| Application examples | C, C++, C#/.NET, Go, Python, and a Web backend |
| Original product scope | One product/multiple plans; perpetual and fixed-term purchases; recurring billing P1. Multiple products have since been implemented |
| Fixed terms | Start at verified payment; UTC calendar anchors with no month-end drift |
| Currency | Baseline tests use USD; verify deployed currencies and never silently convert or merge currencies |
| Web assets | Native HTML/CSS/JavaScript embedded in the binary; no separate Node server |

Dependencies align with the reviewed Licentivo workspace: GORM 1.31.1, GORM MySQL driver 1.6.0, and go-sql-driver/mysql 1.9.3. `go.mod`/`go.sum` pin resolution.

## Local data boundaries

Models cover configuration, secrets, accounts/staff/sessions, products, plans and versions, remote mappings, payment accounts, orders, payments/refunds/events, entitlements, paid coverage, license bindings, jobs, licensing events, and audit.

Payment, order, and license states remain separate. `sandbox/live` follows Launch entitlements, orders, and payment accounts, while one Licentivo connection and plan mapping is shared. One principal entitlement exists per account/product/payment environment, with one current binding and retained replacement history.

Unique constraints do not replace business transactions. A payment transaction must verify ownership, amount, currency, and external identity, then record payment, order, coverage, and licensing task atomically. Serialize tasks per entitlement and retry original IDs/parameters. Refunds lock the original payment and enforce the captured balance. Payment replay must not clear account disablement, manual suspension, or permanent revocation.

Device summaries, release quotas, email credentials, reconciliation, and workers were planned for later stages at M0; consult current progress for their implementation.

## Reviewed Licentivo baseline and compatibility

The original review read a separate local Licentivo server checkout at commit `343c22a3d8c30959119a30ef039f85e7195c4e07`. Its worktree cleanliness was not confirmed. It is not part of this public repository, and the review was not a release compatibility certification.

| Gap | Observed behavior | Integration decision |
| --- | --- | --- |
| GAP01 | Creation does not accept an absolute sales deadline; policy duration starts on activation | Preserve absolute sales coverage locally, provide enough remote duration, suspend at the local deadline |
| GAP02 | Policy change recomputes expiry from activation and policy days | Reread state, ensure remaining coverage, retain device/metering history |
| GAP03 | Batch API stores/replays results by stable UUID | Derive stable `request_id` values for management operations and recover interrupted results |
| GAP04 | Ordinary PATCH lacks sales-entitlement version comparison | Serialize local tasks, check expected remote state, use batch replay for recoverable operations, limit state PATCH to active/suspended |

The official SDK continues to handle activation, signatures, heartbeats, and device credentials. Launch owns sales deadlines and synchronizes remote state through background work; outages can delay deadline suspension. See [licentivo-contract.md](licentivo-contract.md).
